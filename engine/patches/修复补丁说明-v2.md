## 二、逐项技术原理

### 1+2. 条件渲染 + 流式输出（v1 内容，全保留）

- **条件渲染**：PM4 包 `IT_SET_PREDICATION`（机体隐身/遮挡剔除特效的数据开关）此前直接被忽略。补丁在 CP 包解析层捕获 64 位断言缓冲地址，在渲染器用 Vulkan 条件渲染扩展执行绘制跳过。无扩展的老驱动自动降级为 CPU 侧判定，不会崩溃。
- **流式输出**：PM4 包 `IT_STRMOUT_BUFFER_UPDATE`（粒子/残影/贴图特效的顶点流回写）此前被忽略。补丁实现三源（目标地址/源地址/立即数偏移）写入语义，游戏引擎的流式数据链恢复闭环。

### 3. D16S8 深度格式：GTX 960M 上的"能修"与"不能修"（诚实边界）

**不能修的部分**：NVIDIA Maxwell（含 960M）到最新架构，硬件层一律不支持 `VK_FORMAT_D16_UNORM_S8_UINT`。这是驱动/硬件事实，任何软件补丁都无法让硬件"长出"这个格式。引擎现有的回退链（D16S8 → D24S8 → D32S8）方向正确。

**v2 修的部分（实打实的精度 bug）**：Vulkan 规范规定深度偏移（depth bias）的"1 个单位"= 所绑深度格式的**最小可表示值**：

- 游戏按 D16 调的偏移：1 单位 = 1/65535
- 回退到 D24S8 后：1 单位 = 1/16777215
- **同一数值的有效偏移量只剩 1/256** → 贴花陷进墙里/阴影抖动/多边形 z-fighting

补丁在渲染器里记录实际分配的深度格式（`vk_rasterizer` 的 `db_format_actual`），当检测到"游戏请求 Z16 + 实际 D24S8"组合时自动把偏移值 ×256（2^24/2^16）恢复几何意图。GCN 硬件没有 Z24 模式，所以 D24S8 出现必为回退产物，判定无歧义。日志会输出一条 `D16S8 depth format fallback (D24S8) detected: depth-bias units rescaled by 256x` 供你确认补丁生效。

> 深度/模板的读写、清除、深度范围测试、深度边界本身都是归一化浮点语义，格式无关，不受回退影响——受影响的只有多边形偏移这一个精度点，v2 已补。

### 4. 着色器翻译：5 条 clamp 指令（GTX 960M 上贴图烧穿/黑块的候选根因之一）

GCN 指令集有一批"带限幅"的浮点指令，防止溢出值在数据流里传播。旧翻译器把它们**直接近似成无限幅版本**，正常输入下数值一致，但临界输入（0、次正规数、inf）会产生 inf/NaN 并沿 HDR 色调映射、光照衰减、法线归一化链路放大——表现为黑块、白闪、烧穿贴图。

v2 逐条恢复硬件语义（GCN ISA 文档原文行为）：

| 指令 | 旧翻译（近似） | v2 翻译（硬件语义） |
|------|---------------|---------------------|
| `V_LOG_CLAMP_F32` | `log2(x)` | `log2(clamp(x, 2^-126, 2^127))` —— log(0)→-inf、log(负)→NaN 被拦截 |
| `V_RCP_CLAMP_F32` | `1/x` | `clamp(1/x, ±FLT_MAX)` —— x=0 时不再产生 inf |
| `V_RSQ_CLAMP_F32` | `rsqrt(x)` | `clamp(rsqrt(x), ±FLT_MAX)` —— 负数/零输入的 inf/NaN 被拦截 |
| `V_RCP_CLAMP_F64` | **未实现**（目标寄存器残留旧值） | `clamp(1/x, ±DBL_MAX)` |
| `V_RSQ_CLAMP_F64` | **未实现**（同上） | `clamp(rsqrt(x), ±DBL_MAX)` |

F64 两条此前完全缺失：翻译器遇到时静默跳过，目标寄存器保持上一条指令的残留值——**错误数据静默污染**，这是比"近似"更严重的正确性缺口。

**诚实边界**：着色器翻译器有数千条指令，v2 聚焦的是**可实证、可定位、高命中**的这一族。不能宣称"全部翻译近似问题已解决"——那不现实。但这 5 条是 log/rcp/rsq 家族里唯二的精度缺口，且 F64 两条是从"错误"到"正确"的修复。

### 5. clamp 模式：近似已是业界最优，v2 改进的是"可见性"

GCN 的 `MIRROR_ONCE_HALF_BORDER`/`MIRROR_ONCE_BORDER` 需要"镜像一次然后取边框色"，Vulkan 没有对应寻址模式（没有 mirror-clamp-to-border）。RPCS3/yuzu/shadPS4 全体用 `eMirrorClampToEdge` 近似。**差异仅在边框色 ≠ 纹理边缘色的场景可见**（阴影图、贴花边框），v2 维持该映射（客观上限），改进：

- 原实现每次创建采样器都刷一条 WARNING（每帧数百次，刷爆日志还耗 CPU）→ v2 改为每种模式只记一次
- `GetSupportedFormat` 的 D16S8 回退分支补了一条一次性 INFO 日志，与 #3 的补偿日志互相印证
- 差异原理写进本文档，不再是一笔糊涂账

## 三、v2 附带的构建系统补丁（让云端编译真正跑通）

云编译包 v1 的 CI 工作流有一个致命误判：**"依赖已内置源码包"**。实际 45 个 externals 目录在 zip 里是空挂载点（git submodule 结构不带内容），v1 工作流会在 CMake 配置阶段直接失败。v2 修正：

1. **`ffmpeg-cmake-sha-override.patch`**：ffmpeg 预编译包按 git 短 SHA 命名下载，zip 源码无 git 历史。补丁给 `externals/ffmpeg-core/CMakeLists.txt` 增加 `FFMPEG_GIT_SHA` 变量覆盖（CI 传 `-DFFMPEG_GIT_SHA=94dde08`）。
2. **`imguifiledialog-childflags-compat.patch`**：ImGuiFileDialog 当前 HEAD 使用 imgui 1.92 正式的 `ChildFlagsSet` API，而 ext-imgui docking 快照还是老结构，二者 API 断裂（本地实证编译失败于 `ImGuiFileDialog.cpp:4245`）。补丁一行 shim 对齐老快照。
3. **CI 工作流新增"恢复子模块"步骤**：按 `.gitmodules` 从 GitHub 克隆 45 个依赖 + 4 个嵌套依赖（zycore/SPIRV-Headers/dlg/rapidjson），全部浅克隆 8 路并行。

## 五、预期效果与验证方法

装上 v2 引擎后，在 GameBox 里开 `user/logs/shadps4.log` 检索：

- `D16S8 depth format fallback (D24S8) detected: depth-bias units rescaled` → 深度补偿生效
- `Conditional rendering` 相关日志 → 条件渲染生效（v1 已有）
- 原先刷屏的 `Unimplemented clamp mode` 只会在每种模式首次出现一次

游戏内观察点：贴花/阴影的 z-fighting、贴图烧穿黑块、机体隐身（v1）。着色器 clamp 指令是逐着色器生效的，不同游戏命中不同——有改善就是改善，没有命中也不代表补丁无效（该游戏可能没用这些指令）。

## 六、已知限制（不隐瞒）

1. D16S8"硬件级支持"不可能，v2 是回退路径的精度修复，不是让 960M"支持 D16S8"
2. clamp 近似受 Vulkan 表达能力限制，残余差异在边框色场景仍可能可见
3. 着色器翻译器体量巨大，v2 修复的是实证缺口，不是"翻译器完美"
4. 若上游依赖库（45 个子模块）未来 HEAD 变动引入新断裂，CI 可能失败——重跑一次即可（GitHub Actions 克隆的是当时的最新 HEAD）
5. ffmpeg 预编译 SHA 若 404，把 yml 顶部 `FFMPEG_SHA` 改为备选 `b0de1dc` 或 `42557a7`
